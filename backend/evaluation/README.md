# Оценка на фотографиях

Реальных фотографий пока нет; точность, latency и стоимость AI **не измерены**.
`dataset.template.json` намеренно пуст. Evals запускаются вручную, отдельно от
`tests/` и CI. Без `--allow-paid` нет HTTP-запросов, даже к backend. `--local-fake`
разрешает только явно выбранную демонстрационную проверку механизма.

## Формат

Скопировать шаблон в `evaluation/private/dataset.json`; фото хранить в той же
приватной папке. Не добавлять имена людей, геолокацию или другие персональные
данные. ID — произвольный идентификатор, например `case01`. Все поля обязательны;
неизвестные поля запрещены. Пример структуры **для заполнения**, без эталонных
чисел или результатов:

```json
{
  "schema_version": "1",
  "cases": [{
    "id": "case01",
    "photo": "case01.jpg",
    "category": "plov",
    "food_expected": true,
    "known_name": "Плов",
    "accepted_names": ["Палау", "Pilaf"],
    "ingredients": [],
    "recipe": null,
    "weighed_mass_grams": null,
    "reference": {
      "reliable": false,
      "source": null,
      "nutrients": null,
      "notes": "Состав и взвешенная порция ещё не предоставлены"
    }
  }]
}
```

Если есть надёжный эталон: `reliable=true`, обязательны измеренная масса и
`nutrients={calories,protein,fat,carbs}` для **этой взвешенной порции**, а также
`source`: этикетка/URL справочника/расчёт рецепта с массами ингредиентов и выходом.
`ingredients` и `recipe` заполнить известными данными; неизвестное не угадывать.
Для рецепта учесть готовый выход/воду и источник каждого ингредиента. При
сомнительном источнике поставить `reliable=false`, объяснить в notes.

Категории: `simple`, `mixed_plate`, `plov`, `manty`, `beshbarmak`, `soup_sauce`,
`poor_light`, `no_food`. Подготовить хотя бы один пример каждой категории;
плохое освещение желательно сравнить с хорошим для того же блюда. Для no_food:
`food_expected=false`, нет пищевого эталона, `reliable=false`.

## Запуск

Из `backend`, после установки lockfile:

```powershell
.venv\Scripts\python.exe -m evaluation.run --dataset evaluation/private/dataset.json --output evaluation/private/run01.json
.venv\Scripts\python.exe -m evaluation.selftest
```

Ограниченный платный запуск после собственного решения пользователя:

```powershell
$env:TAMAQ_PILOT_TOKEN_FILE = (Resolve-Path var/pilot-token.json).Path
.venv\Scripts\python.exe -m evaluation.run --dataset evaluation/private/dataset.json --output evaluation/private/run01.json --url https://YOUR-SERVICE.onrender.com --allow-paid --max-cases 2 --max-cost-usd 0.60
```

Код приглашения/получение токена — `docs/DEVELOPMENT.md`. Harness обращается только к
backend, ключ OpenAI не нужен на компьютере с evals. Лимит учитывает $0.30 перед
каждой возможной попыткой, затем usage или полный резерв неизвестного исхода.
В текущей проверке разрешён максимум $1 суммарно, включая smoke, телефон и evals,
внутри общего pilot cap $5. Сервер должен иметь сохранённый verification ceiling;
клиент отказывает до POST при его отсутствии. Запускать после успешного реального
smoke и проверки оставшегося бюджета, независимо от даты/CLI-журнала.
Дополнительно действуют общий pilot cap и квоты приглашения 2/мин и 10/UTC-день
(smoke тоже входит). Между примерами пауза 31 секунда. После ошибки/неизвестного
исхода запуск останавливается. Повтор с тем же output-файлом пропускает все уже
отправленные и неопределённые случаи. Новый журнал означает новые возможные
расходы; не создавать его для обхода неопределённого результата.

## Что измеряется

- Наличие еды и нормализованное совпадение названия с заранее заданными aliases.
  Alias match — ограниченная автоматическая метрика. Просмотреть приватные
  ответы и заполнить `recognition_manual_review` как `correct/wrong/uncertain`;
  локальные синонимы не считать ошибками без просмотра. Ручные оценки сохранять
  отдельно от неизменённого исходного журнала; точность по aliases не равна
  доказанной точности распознавания ингредиентов/рецепта.
- Отдельно масса: сумма известных mass_grams, coverage, абсолютная/относительная
  ошибка против взвешенной порции. Если хоть одна масса неизвестна, ошибку массы
  не рассчитывать; неизвестная масса не означает нулевую ошибку.
- Абсолютные ошибки kcal/Б/Ж/У только для надёжных эталонов. Относительные ошибки
  при эталоне ≥10 kcal или ≥1 g соответствующего макронутриента; иначе null.
  Это ошибки оценки всей видимой порции. Изменение порции пользователем в Android
  не входит в сырые AI метрики и должно оцениваться отдельно, если потребуется.
- HTTP round-trip latency (включая upload, backend и получение receipt), median/max.
  Usage-priced стоимость отдельно от неопределённого резерва. Invoice OpenAI —
  окончательный источник списаний; тарифный расчёт нужно сверять с ним.
- Refusal, ambiguous/no_food, технические ошибки и число валидных примеров `n`.
  Не считать пропущенные/ненадёжные эталоны нулевыми ошибками. Отказы показываются
  отдельно, а не входят в технические ошибки.

Журнал сохраняет модель, prompt/schema/pricing version, параметры, timestamp,
анонимный case ID, digest нормализованного снимка, UUID до отправки, ответ/receipt,
usage и метрики. Фото не копируются в журнал. Из stdout исключены названия блюд,
пути фото и ответы; они доступны только в **приватном** output JSON. Ограничьте
ACL папок/срок хранения журнала; `.gitignore` не заменяет контроль доступа.
